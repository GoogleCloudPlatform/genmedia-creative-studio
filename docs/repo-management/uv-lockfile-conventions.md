# uv Lockfile Conventions

> **Purpose:** state the one rule that keeps this project's Python dependencies consistent —
> *`uv.lock` is the single source of truth; an exported `requirements.txt` is a derived artifact
> that must be regenerated by a full re-resolve, never hand-edited* — and explain why, with the
> real incident that proved it.

Several Python components in this repository are managed by [`uv`](https://docs.astral.sh/uv/),
a fast Python package and project manager. This document is the **reusable convention** for how
those components track their dependencies, so they don't quietly drift into an un-installable
state. The incident that motivated it is cited afterward as the worked example.

> **Resolve (dependency resolution):** the step where a tool reads every package you ask for,
> follows each package's own requirements, and computes one set of exact versions that satisfy
> *all* of them at once. A "lock" is the frozen output of that computation.
>
> **Transitive dependency:** a dependency of a dependency. You depend on library A; A depends on
> library B; B is *transitive*. You never named B, but its version rules still constrain what can
> be installed — and conflicts often hide there.

## The convention

For any Python component managed by `uv`, **`uv.lock` is the single source of truth** for
dependencies. It is the fully-resolved, internally-consistent record of every version — direct
and transitive — that the component installs.

Some components also commit an **exported `requirements.txt`**: a flat, pip-readable list
generated *from* the lock (via `uv export` or `uv pip compile`). An export is a **derived
artifact**, not an input. Two rules follow:

- **When both are committed, the export must be regenerated from a fresh full re-resolve**
  (`uv lock --upgrade`) whenever the lock changes — **not** from a narrow, single-package edit.
  A hand-edited or partially-regenerated export can disagree with the lock, and that disagreement
  is exactly where breakage hides.
- **Ideally the export should not be committed at all** unless something actually consumes it — a
  Docker build, a script, an audit tool. An export that nothing reads is pure liability: it can
  drift, but nothing depends on it being correct.

### Who this affects: the drift-prone set

These components currently commit **both** a `uv.lock` and an exported `requirements.txt`. Because
the two can disagree, they are the ones that need care:

| Component | Export generator command | Is the export consumed? |
|---|---|---|
| `.` (core app) | `uv export --format requirements-txt --no-hashes` | Near-vestigial. The Docker build uses `uv sync` (not the export), and CI uses `uv run`. The **only** consumer is `scripts/local_security_audit.sh`, whose `PIP_AUDIT_REQUIREMENTS` defaults to `requirements.txt`. |
| `archive/arena` | `uv export --no-hashes --no-annotate --format requirements-txt --frozen` | **Archived (2026-09-13).** Moved from `experiments/arena` to `archive/arena`; retained for reference only and no longer maintained (Renovate disabled for `archive/**`), so this convention no longer applies in practice. **Decommissioned 2026-10-05:** the `archive/arena/Dockerfile` and `Procfile` were removed, so the component is no longer buildable/deployable and nothing consumes this export. |
| `experiments/babel/app` | `uv pip compile pyproject.toml` | **Yes** — `experiments/babel/app/Dockerfile` runs `pip install -r requirements.txt`. |
| `experiments/mcp-genmedia/sample-agents/adk` | `uv export --format requirements-txt --no-hashes` | No — there is no Dockerfile, and the component's README instructs `uv sync`, so nothing reads the export. |
| `experiments/promptlandia` | `uv export --format requirements-txt` (with hashes) | No — no Dockerfile consumes it. |

The commands above are abbreviated: most also end in an output flag such as `-o requirements.txt`.
Always use the **exact** command recorded in the autogenerated header at the top of each component's
`requirements.txt` rather than the shortened form here.

### The safe shape, for contrast

Several components commit **only** `uv.lock` and no export — for example
`experiments/countdown-workflow`, `experiments/veo-genetic-prompt-optimizer`,
`experiments/veo-variations`, and `experiments/veo3-character-consistency`. These have **nothing
to drift**: there is no second file to fall out of sync, because Renovate and `uv` re-resolve the
lock directly. **This is the preferred shape.**

## Why this matters: the real incident

The drift is not hypothetical. It comes from *two* automated dependency managers acting on the
same component without knowing about each other.

Renovate — the dependency-update bot — has two relevant managers:

- Its **`pip_requirements`** manager edits a committed `requirements.txt` with a **naive
  single-line version bump. It does not re-resolve**, and it has no idea the file was produced by
  `uv export`.
- Its **`pep621`** manager reads `pyproject.toml` and **does** correctly re-resolve `uv.lock` via
  the `uv` CLI — but it is a *separate* manager that never touches the export.

The two run independently over the same component. One updates the lock correctly; the other
hand-edits the export incorrectly; nothing reconciles them.

### PR #1757 (broken) → PR #1804 (fixed)

Renovate bumped `google-cloud-aiplatform` to `2.1.0` on its single line in the core
`requirements.txt`, but left `protobuf==7.36.1` untouched. `aiplatform 2.1.0` caps
`protobuf<7.0.0`, so the exported file became internally contradictory — it required protobuf 7.x
and forbade it at the same time.

> **`ResolutionImpossible`:** the error a resolver raises when the version constraints contradict
> each other, so *no* set of versions can satisfy them all. Here, one line demanded `protobuf`
> below 7.0.0 while another pinned it at 7.36.1 — impossible.

**Why CI didn't catch it:**

1. `python-tests.yml`'s path filters do **not** trigger on `requirements.txt`, so a change to
   that file alone doesn't even run the workflow.
2. Even when CI *does* run, it installs via `uv run` / `uv.lock` — it **never installs the
   exported file**.

So the export files were simultaneously the only thing Renovate hand-broke, not covered by CI,
and (for core) not even used by the build.

**The correct fix (#1804)** regenerated the lock and export with a full `uv lock --upgrade`. That
dropped `protobuf` to the `6.33.x` range and brought the whole lock current in one consistent
re-resolve. A *narrow* fix (`uv lock --upgrade-package` on the stale base) had rolled roughly 60
unrelated packages **backward** — including a major OpenCV downgrade — which is exactly why the
**full** `--upgrade` is required rather than a targeted one.

## The recommended fix pattern

If you touch dependencies in a component that commits an export, follow these steps:

1. **Re-resolve the whole lock first:**
   ```
   uv lock --upgrade
   ```
   A full re-resolve — **never** a narrow package-only upgrade on a possibly-stale base. A
   package-only upgrade mixes your intended bump with whatever unaudited, stale state the lock was
   already in.

2. **Verify the lock is in sync with `pyproject.toml`:**
   ```
   uv lock --check
   ```

3. **Regenerate the export in the *same* commit** — only if something genuinely consumes it — using
   that component's **exact** export command (it's recorded in the autogenerated header at the top
   of the `requirements.txt`). For the core app, for example:
   ```
   uv export --format requirements-txt --no-hashes -o requirements.txt
   ```
   **Never hand-edit a single line in an exported file.**

4. **If nothing consumes the export, don't commit it.** Delete it and let `uv.lock` be the single
   source of truth. The safest export is the one that doesn't exist.

## Follow-up / future direction

The following are **recommendations, not current state.** Neither is in place today; they are
recorded here so the direction is clear.

- **A CI lockfile-drift check (proposed).** For each component that still commits an export, CI
  would regenerate the export from `uv.lock` using that file's exact flags and **fail on any
  diff**, alongside a `uv lock --check`. This would catch drift *regardless of cause* — a Renovate
  hand-edit, a manual edit, or a stale merge — instead of relying on reviewers to spot it.

- **A Renovate config stop-gap (complementary, not yet applied).** Disable `pip_requirements`
  hand-edits of these exported files and enable `uv.lock` `lockFileMaintenance`, so Renovate only
  ever touches the source of truth. This complements the CI check rather than replacing it.

## The lesson

- **One source of truth.** `uv.lock` is authoritative; a `requirements.txt` export is derived.
- **Full re-resolve, never a line edit.** A one-line version bump on an exported lock is exactly
  the change most likely to be silently broken — regenerate from `uv lock --upgrade`.
- **Don't commit an export nothing consumes.** A file that can drift but that nothing reads is all
  risk and no benefit; delete it and let the lock stand alone.
